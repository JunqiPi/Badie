# Badie v3 · 设计说明（Court Pop）

本文记录这次全面改版的设计过程与结论，按设计师的真实工作步骤组织：
**发现 → 定义 → 构思 → 高保真验证 → 系统化 → 实现与走查**。

数据来源标注：**[用户]** 真实用户帖子/评论，**[媒体]** 报道，**[厂商]** 官方自述（未独立验证），**[论文]** 学术研究。

| 资料完整更易获得信任 | BlaBlaCar × NYU 调查 [厂商] | 资料卡展示等级、口碑、履约率、距离；手机号永不展示 |
| Playtomic 的分摊付款与按位预付口碑好 | App Store 4.8 / 1.4 万评分 [用户] | AA 明细透明、平台不收服务费（真实支付需后端接入） |

## 2. 定义（Define）

**核心任务（JTBD）**：“今晚 / 这周某个时间，在我能去的球馆，找到水平差不多、靠谱的人打一场。”

**设计原则**

1. **一眼可读**：大数字、强对比、墨色描边；时间、价格、人数用圆体数字突出。
2. **有分量的触感**：硬投影按钮按下时“压平”，配合触感反馈；动画都能被“减弱动态效果”关闭。
3. **信任可见**：任何出现球友的地方都带等级、准时率、履约率；新球友明确标注“待校准”。
4. **少一步**：默认今晚 19–21、常用时间、最近的球馆、偏好模式；首页一键“开始匹配”。
5. **活力不吵闹**：柠檬绿只用于最重要的行动；其余用马卡龙“贴纸色”区分信息类型。

## 4. 高保真验证（Prototype）

在写 SwiftUI 之前，先用 HTML 做了风格板 + 4 个关键页面（首页、找到搭子、球局票、我的）的浅色/深色高保真稿，渲染后自查并迭代了一轮：

- 深色模式第一版描边几乎不可见 → 改为浅紫灰描边，并做了对比度复核（见下表）；
- 柠檬色马克笔高亮在深色下“白字压亮绿”不可读 → 高亮文字统一改为墨色；
- VS 星形压住对手昵称 → 下移到卡片下方。

最终界面以 CI 中的模拟器截图做走查（`scripts/ci_screenshots.sh`，浅色/深色各 19 个页面）。第一轮走查（Design QA）发现并修复：

- 悬浮标签栏四周会露出滚动内容（首页日期条、我的页卡片）→ 标签栏后加画布色渐隐底；
- 通知未读底色（黄色 35% 透明）在深色下变成发灰的橄榄色 → 改为“未读 = 浮起的白卡，已读 = 平铺的浅灰卡”，靠层级而非色相区分；
- 房间详情里“编辑时间和球馆”是一行孤立文字链接 → 改成与其他信息行对齐的菜单行（带图标与箭头）。

## 5. 设计系统（`Badie/DesignSystem/`）

### 5.1 颜色 Token（浅色 / 深色）

| Token | 浅色 | 深色 | 用途 |
|---|---|---|---|
| canvas | `#F5F0E6` | `#16131D` | 页面背景 |
| surface | `#FFFFFF` | `#221E2B` | 卡片 |
| surfaceMuted | `#EDE6D8` | `#2C2737` | 次级底色、禁用 |
| ink | `#17140F` | `#F4EFE6` | 正文/标题 |
| inkSecondary | `#5B554B` | `#B9B2A6` | 次要文字 |
| inkTertiary | `#8C8579` | `#857D90` | 装饰/禁用（不承载关键信息） |
| stroke | `#17140F` | `#756A90` | 描边 |
| shadow | `#17140F` | `#07060A` | 硬投影 |
| lime | `#D4F33F` | 同 | 主行动（只作填充色） |
| lavender / peach / pink / sky / butter / mint | 马卡龙 | 略加深 | 社交 / 球局 / 评价 / 地点 / 成就 / 状态 |
| onAccent | `#17140F` | 同 | 所有强调色上的文字 |
| danger / dangerFill | `#C92A2F` / `#D22F35` | `#FF6B6E` / 同 | 错误文字 / 角标 |

**对比度复核（WCAG 2.1）**

| 组合 | 对比度 | 结论 |
|---|---|---|
| ink / canvas（浅） | 16.2 : 1 | AAA |
| inkSecondary / canvas（浅） | 6.5 : 1 | AA |
| onAccent / lime | 14.6 : 1 | AAA |
| onAccent / 各马卡龙色 | 10.7–14.4 : 1 | AAA |
| ink / surface（深） | 14.2 : 1 | AAA |
| inkSecondary / surface（深） | 7.8 : 1 | AAA |
| danger / canvas（浅 / 深） | 4.8 / 6.6 : 1 | AA |
| 白字 / 红色角标 | 5.0 : 1 | AA（由 3.9 调整而来） |
| 描边 / 画布（深，非文字） | 3.7 : 1 | 满足 1.4.11 的 3:1（由 1.9 调整而来） |

规则：**柠檬绿永远不当文字色放在浅色背景上**；强调色上的文字统一用 onAccent。

### 5.2 字体

全部基于系统文本样式（自动支持动态字体），`design: .rounded`：Display = largeTitle Black，Title / Title2 Heavy，Headline Bold，Body Medium……
固定大字号（票据时间、统计数字）用 `scaledFont(size:)`（`@ScaledMetric`），同样跟随动态字体缩放。中文回落为苹方。

### 5.3 间距、圆角、描边、投影、动效

- 4pt 栅格：2 / 4 / 8 / 12 / 16 / 20 / 24 / 32；页面边距 20。
- 圆角：10 / 14 / 20 / 26（连续曲率）。
- 描边 2pt；卡片硬投影 (3, 4)；按钮垂直投影 4pt，按下时下沉 4pt（“压平”）。
- 动效：standard spring(0.35, 0.78)；press 0.12s；碰撞动画 0.7s。系统开启“减弱动态效果”时，跳过弹跳、旋转、粒子与轨道动画。

### 5.4 组件

`StickerBackground`（`.sticker()` / `.card()`）、`BrutalButtonStyle`（primary / inverse / secondary / destructive / accent × large / medium / small）、`IconTile`、`IconButton`、`CountBadge`、`AvatarView` / `AvatarStack`、`LevelBadge`、`TagPill`、`NewPlayerBadge`、`ChoiceChip`、`SegmentedSticker`、`DateStrip`、`TimeStepper`、`LevelStepper`、`RatingPicker`、`BrutalTextField`、`SearchField`、`StatTile`、`InfoRow`、`MenuRow`、`SectionTitle`、`ScreenHeader` / `LargeTitleHeader`、`TicketShape`、`Starburst(Badge)`、`ShuttlecockMark`、`Wordmark`、`ToastView`、`NoticeBanner`、`EmptyStateView`、`LoadingDots`、`ProgressBar`、`FlowLayout`、`FloatingTabBar`。

## 6. 信息架构与核心流程

```
启动 → 欢迎 → 手机号(+隐私同意) → 验证码 →（新用户）昵称/头像 → 自评等级 → 偏好(模式/常用时间/定位)
                                         ↘（老用户）直接进入
主框架（悬浮标签栏）
├─ 首页：下一场球票 · 快速约球卡 · 哪天有空(可约人数) · 待评价 · 附近球局 · 附近球友 · 附近球馆地图
├─ 球局：发起球局 / 房间码 · 我的房间 · 即将开始 / 已结束 · 历史
├─ ＋：快速匹配 / 发起球局 / 输入房间码
├─ 消息：聊天（已读回执、输入中、房间邀请卡、快捷回复、屏蔽/举报）· 球友（申请、搜索、加好友）
└─ 我的：资料 · 口碑与等级校准 · 履约记录 · 球友 · 常用时间 · 出行范围 · 球馆收藏 · 屏蔽名单 · 设置
```

**快速匹配（约球请求）**：设置（模式 / 14 天内日期 / 1–8 小时时段 / ≤3 个球馆 / 水平差 / 是否自动接受）→ 发起请求 → 后台持续匹配（首页、球局页显示请求卡片）→ 找到搭子（靠谱徽章与正面印象、共同空闲时间、球馆、AA 明细、双打自动平衡分组）→ 每个人确认 → 全部确认才生成球局票。详见 §10。
暂时没人时：显示真实的“附近有空 / 条件都合适”人数，只展示**确实能找到人的**放宽方式；到点没约成自动结束、不计入记录，可转为临时局或发起公开球局。

**球局生命周期**：确认 → 提醒（三次）/ 加入日历 / 导航（Apple · 高德 · 百度）/ 聊天 → 开赛前 30 分钟签到 → 结束并记录结果 → 双盲互评（到场情况 / 水平三选一校准 / 球品 / 标签）→ 口碑与综合等级更新。

## 7. 无障碍

- 所有图标按钮都有 `accessibilityLabel`，选中态带 `.isSelected`；卡片合并为单个可读元素。
- 动态字体：全部使用文本样式或 `@ScaledMetric`。
- 减弱动态效果：启动弹跳、匹配雷达、轨道头像、碰撞动画均降级为静态或淡入。
- 点击区域不小于 44×44pt；时间与等级步进器支持 VoiceOver 的上下滑动调整（`accessibilityAdjustableAction`）。
- 颜色不是唯一信息来源：状态同时有文字（“已付 / 待付”“已读 / 已送达”）。

### 多语言

- 界面语言：简体中文（源语言）、English、繁體中文、日本語、한국어、Bahasa Indonesia、Bahasa Melayu、ไทย、Tiếng Việt、हिन्दी——覆盖主要羽毛球国家（中、印尼、马来西亚、日、韩、泰、越、印度、丹麦等北欧用户用英文）。设置 → 语言跳到系统的 App 语言设置。
- 文案都在 `Localizable.xcstrings` / `InfoPlist.xcstrings`，以中文原文为键。新文案用 `Text("…")` 或 `String(localized: "…")`；需要高亮的词写在同一句里用 `*星号*` 包住（`Text(marking:)`），不要拼接碎片，否则其他语言无法调整语序。
- 以中文存储的枚举 rawValue 不直接显示，统一用 `title`。日期、时刻、列表连接（`formatted(.list)`）跟随系统地区。
- CI 每次构建导出待翻译文案（`localizations` 产物）；单元测试固定在简体中文下运行；截图另有英文全套和各语言抽查。
- 演示数据（模拟球友的昵称、签名、聊天、球群介绍）属于用户内容，不翻译。

## 9. 球馆：怎么保证大家选的是同一家（首发美国，面向全球）

> 问题来源：“我会选 LABC / Elite Rally 然后在地图上找，万一找不到呢？”匹配只有在两个人选中**同一个球馆**时才成立。

### 9.1 先看真实情况（2026-10 实测）

| 观察 | 证据 | 结论 |
|---|---|---|
| 同一家球馆，不同来源写着不同城市 | Elite Rally（4800 Rivergrade Rd Unit B）：Yelp 写 Baldwin Park，Atly 写 Irwindale，另一篇文章写 Santa Fe Springs | 名称、城市都不可靠，必须看**完整地址 + 地图位置** |
| 按名称搜会搜到错的地方 | OpenStreetMap 搜 “Los Angeles Badminton Club” 返回 40 公里外 Manhattan Beach 的 “Badminton Club Pool”（游泳池）；Elite Rally 在 OSM 里不存在 | 不能只靠第三方地图的名称匹配 |
| 地图平台没有“羽毛球”分类 | Apple `MKPointOfInterestCategory` 84 个分类里有网球、排球，没有羽毛球 | 只能关键词搜索 + **自建球馆库** |
| 用户添加的球场目录容易变脏 | Pickleball+ App Store 评论 [用户]：信息过时、有人把自家房子加成球场；Places2Play 需要审核 [厂商] | 新球馆要有“待确认”状态和举报机制 |
| 重复球馆来自“直接新建” | The Events Calendar 组织者 [用户]：“大量重复的场馆”，因为回车就新建 | “添加球馆”放在结果底部，先查重再新建 |
| 只显示名字不够 | Baymard 自动补全研究：突出差异部分、移动端 4–8 条；Teevan 等 MobileHCI 2011：约 60% 的本地搜索不在身边 [论文] | 每行显示地址；按距离排序但**不限制**范围 |

### 9.2 方案

1. **平台球馆库是唯一标准**：匹配、房间、球局只比较我们自己的球馆 ID。Apple Place ID（iOS 18+）只作为附加字段用于查重（Apple 说明同一地点可能有多个 ID，因此连同 `alternateIdentifiers` 一起比较）。
2. **一个搜索框，两层结果**：先“已选 / 常去 / 附近”，输入后先显示球馆库（名称、别名、英文缩写 LABC、中文拼音首字母、街道、城市、邮编都能搜），再显示 Apple 地图联想（最多 6 条）。
3. **每一行都有地址**：名称（高亮匹配部分）+ 距离 / 街道·城市·州 / 可信度（已核实 · 球友确认 · 待确认）+ 场地数 + 常去人数。完整地址、地图在核对页和详情页。
4. **地图结果先核对再入库**：地图预览 + 完整地址 + 查重（Place ID 相同 → 直接选已有；200 米内名称相近 → “是同一个吗？”；40 米内同一栋楼 → 让用户判断，不自动合并，因为同楼可能有不同场馆）。
5. **找不到就添加**：移动地图让图钉对准入口 → 自动识别地址（可改）→ 名称 / 简称 / 单元 / 入口说明 / 场地数 → 查重 → 加入。也可粘贴 Google / Apple 地图链接（群聊里最常见的分享方式），自动解析坐标、名称或 Place ID。
6. **可信度会成长**：新加入为“待确认”，3 位不同球友确认（或在此签到打过球）后变为“球友确认”；显示“最近确认”时间。一个人举报不会下架，2 人以上举报的待确认球馆暂时从搜索中隐藏、等待人工核实（添加者本人仍可见）。
7. **少选几次**：常去球馆默认进入快速匹配；常去不受出行范围限制。
8. **新球馆别人马上能选，但不会把库弄乱**：
   - 新加的球馆立刻出现在别人的搜索里（排在已核实的后面，标“待确认”）。
   - **近似重复直接拦截**：Place ID 相同 → 直接用已有的；200 米内名称相近 → 不能新建，只能选已有的（查重结果放在添加页最上方）。同一栋楼但名称不同 → 允许（可能是不同场馆），标记给人工复核。
   - 每人每天最多添加 3 个球馆；重复条目由审核合并，旧 ID 自动跳到保留的那家，收藏、请求、旧名称（变成别名）一并转移。
9. **匹配要求球馆对得上**：只有双方都能去的球馆才会被安排。同一 ID、已合并、或相距 150 米以内（同一栋楼 / 园区）视为同一处——所以有人新加了“LABC 2 号馆”，也能和选 LABC 的人匹配上；一个只有自己知道的新球馆，在别人也选它之前不会匹配到人。

### 9.3 全球化（数据层已就绪）

| 项 | 做法 |
|---|---|
| 地址 | 结构化存储（街道、单元、城市、州/省、邮编、国家码），按国家习惯格式化（美式由小到大，中日韩台由大到小） |

## 10. 约球请求：后台排队 + 多方确认

> 问题来源：“匹配较长的话是不是应该收起来作为一个 queue？”“我接受了，对面拒绝了怎么办？”“打球前两小时必须确认吧？那 30 分钟后的临时局呢？”

### 10.1 依据（论文优先，其次是被广泛使用的产品做法）

| 结论 | 证据 |
|---|---|
| 不该让人盯着转圈等 | 手机通知通常几分钟内就会被看到 [Pielot 等 2014]；约球的人不会一直在线，供需两边都要“挂单” [Kanoria & Saban, Management Science 2021：平台替双方做筛选能减少无效沟通] |
| 平台提议，一人同时只挂一个提议 | 同时向太多人发邀约会造成拥堵、回复率下降 [Arnosti, Johari & Kanoria, MSOM 2021]；Hinge 限制同时进行的对话后回复率提升 [产品公告] |
| 可选“自动接受” | Airbnb 即时预订：被拒的客人之后预订概率明显降低 [Fradkin 等]；提前声明“符合条件就去”= 预先接受 |
| 确认期限随距开赛时间放宽 | 期限太短会逼人仓促决定，太长又会占着名额 [Niederle & Roth 2009 关于“爆炸性 offer”]；Playtomic 等订场 App 的取消规则按距开赛时间分档 [产品] |
| 拒绝/超时不公开扣分，只罚爽约和临时取消 | Uber 加州 2020 年取消接单率惩罚后，大量司机拒单率变得极高 [新闻报道]；惩罚“说不”会让人不敢挂单 |
| 不告诉大家是谁拒绝的 | 公开拒绝者会带来报复与尴尬，互评研究同理（见 §11 eBay 案例） |

### 10.2 规则

| | 普通局（开赛 > 2.5 小时） | 临时局（开赛 ≤ 2.5 小时） |
|---|---|---|
| 匹配谁 | 那天有空、水平/时间/球馆都对得上的球友 | 只找 5 英里（8 公里）内**此刻也在找人**的球友 |
| 确认期限 | 开赛 ≥26 小时：12 小时；≥6 小时：2 小时；更近：30 分钟 | 1 小时内开赛：5 分钟；否则 10 分钟 |
| 锁定 | 开赛前 **2 小时**必须全部确认（与“2 小时内取消算临时取消”一致） | 开赛前 **20 分钟**必须确认完 |
| 最晚发起 | — | 开赛前 30 分钟 |

- **全部确认才成局**；确认前看到的是“确认进度”（已确认 ✓ / 等待确认），有人来不了时只显示“补位中”，不显示是谁。
- **有人没确认**：双打在锁定前自动找人补位（最多 3 次），已确认的人不用重新确认；单打直接帮双方各自重新排队。补不上就作废，已确认的人**优先**重新排队，不计入任何记录。
- **双打到点只剩 2 人确认**：问两人要不要改打单打（需重新确认，期限 10 分钟）。
- **自己没确认**：请求暂停（不再给不在线的人发提议），点“继续找”即恢复；不扣分。
- **到点没约成**：请求自动结束、不计入记录；普通局可以一键“转为临时局继续找”。
- 确认之后再取消，才按原规则计入履约记录（开赛前 2 小时内 = 临时取消）。

实现：`Models/Matchmaking.swift`（`MatchTiming` 时间规则、`MatchTicket`、`MatchOffer`），`Services/Backend/MockBackend+Matchmaking.swift`（提交、匹配、确认、补位、锁定、到期处理），`Features/Matching/`（等待页、确认页、请求卡片）。

## 11. 口碑怎么显示：分数不公开

> 问题来源：“能看到自己的球品分数，不会导致问题吗？Uber 那些是因为这辈子都不一定能见面了吧？”——同意这个判断：羽毛球是熟人圈子，会反复碰面，公开分数更容易变成人情分或报复。

| 结论 | 证据 |
|---|---|
| 互相能看到评分 → 报复与“互相给好评” | eBay 允许卖家给买家差评时，报复性互评很常见；取消后基本消失 [Bolton, Greiner & Ockenfels, Management Science 2013] |
| 公开的星级会越来越虚高、失去区分度 | 给差评有社交成本，平均分逐年上涨 [Filippas, Horton & Golden, “Reputation Inflation”] |
| 双盲提交能让评价更真实 | Airbnb 同时揭晓评价的实验 [Fradkin, Grewal & Holtz] |
| 针对“人”的分数反馈常常适得其反，针对具体行为的客观反馈更有效 | 反馈干预元分析：约三分之一的反馈让表现变差，越指向自我越糟 [Kluger & DeNisi 1996]；私下给司机看客观驾驶数据能改善驾驶 [Athey 等，Uber 驾驶质量研究] |
| 只给正面标签的做法被广泛接受 | Reclub 的 Kudos、TaskRabbit 的技能标签等 [产品] |

规则：

- **球品分、信誉分只在内部用于匹配排序和审核**，任何人（包括本人）都看不到数字；评价页明确写“只用于匹配排序，不会显示分数”。
- **本人看到自己的客观记录**：准时到场比例、等级偏差、完成 / 爽约 / 临时取消次数、水平校准进度。
- **别人只看到正面信息**：“靠谱”徽章（打满 3 场、没有爽约、临时取消 ≤1 次，只看客观记录）和球友给得最多的正面标签。
- **正面标签有门槛**：≥5 位不同球友、≥3 场后才出现；一个标签至少 2 位不同球友给过才展示；**每月统一刷新一次**，避免从变化反推出是谁评的。
- **问题只私下提醒**：评价时可以选“动作危险 / 言语不友善 / 抢球 / AA 没结清”，不公开、不计分；60 天内 ≥3 位不同球友提到同一点时，私下给本人发一条建议式提醒（不说是谁），同一问题 60 天内只提醒一次。
- 数字等级（Lv）保留：它描述的是球技，不是人品，而且需要用来匹配。

实现：`Models/Reputation.swift`（`publicTags`、`recurringIssues`）、`Models/Survey.swift`（`SurveyIssue`）、`MockBackend+Games.swift`（`sendPrivateNudges`、`publishReputationIfNeeded`）、`DesignSystem/Identity.swift`（`ReliableBadge`、`PraiseTagsView`）。

## 12. 社区与社交：长在“局、球群、球馆”上，不做发帖广场

> 问题来源：“社区功能和社交功能应该加入吗？无论如何用户应该可以点击对方的头像看个人页面。”

### 12.1 依据

| 结论 | 证据 |
|---|---|
| 美国华人羽毛球现在靠微信 / WhatsApp 群接龙、Meetup、场馆系统；痛点是群消息多、新人难融入 | Brooklyn Badminton Center 用微信/WhatsApp 群发空位 [厂商]；湾区论坛常年有贴微信号招球友的帖子 [用户]；有球群“一天 600+ 条消息” [报道] |
| 小圈子里的公开内容流一定冷清 | 健康社区约 1% 的人贡献约 75% 的内容 [van Mierlo, JMIR 2014]；El Monte 的 Meetup 羽毛球群 1,410 人、每场只来 2–5 人 [用户]；RacketPal：“一个活跃玩家都没有” [App Store] |
| 用户最认可的是组织工具 | Pickleheads（“球群离开了短信”）、Reclub（“交到很多朋友”）的好评 [App Store]；Playtomic 用户：“别让它变成社交媒体” [App Store] |
| 比较能带动运动，但要比出勤、不比水平 | 运动在朋友间传染 [Aral & Nicolaides, Nat. Commun. 2017]；有社会比较的组出勤高约 90% [Centola 等 2016]；DUPR 用户反映水平榜催生小号压分 [App Store] |
| 陌生人随意私信是骚扰和诈骗入口 | 50 岁以下用约会应用的女性 56% 收到过不请自来的露骨信息 [Pew 2023]；RacketPal 上有人一上来就要 WhatsApp [App Store] |
| 精确位置 / 距离会被反推 | 95% 中度活跃用户的受保护地点可被推断 [Hassan 等, USENIX Security 2018]；Strava Flyby 曾暴露陌生女性住址 [报道] |

说明：Reddit 不允许抓取，用户证据主要来自 App Store 评论、论坛、Hacker News 与 Meetup 页面。

### 12.2 做了什么

| 功能 | 规则 |
|---|---|
| **点头像看资料** | 任何出现别人头像的地方都能点开资料页；资料页有“你们的交集”：一起打过几场、最近一次在哪、共同球友 |
| **资料页对外信息** | 等级、偏好单打/双打、靠谱徽章、正面印象、场次分档（“20+ 场”）、大概距离（“5 英里内”）。不显示胜率、精确距离、日程、好友列表、在线状态 |
| **私信规则** | 好友随便聊；同一场已确认的球局用**球局群聊**（确认后开放、赛后 48 小时关闭）；同一个球群可以发**一条消息请求**（纯文字，不能留链接或联系方式），对方接受后才能继续，忽略对方不会知道；新账号打满 3 场前不能发请求；陌生人只能发好友申请 |
| **防骗提示** | 非好友的消息里出现手机号、微信、WhatsApp、Venmo/Zelle 等时，在聊天里提醒“见面打球前不需要转账、代付或验证码” |
| **球群（固定局）** | 组织者建群并绑定球馆；每周固定场次；一键报名，满员自动候补，有人退出按顺序自动递补并通知；开场前 2 小时内退出算临时取消；组织者可审批加入、取消某一场；群号可以发到微信，在“房间码 / 群号”里加入；对外只显示“近 30 天几场、平均几人”，不显示成员总数 |
| **同馆常客**（替代“附近球友”） | 只显示和我常去同一家球馆、并且**本人开启了**的球友（默认关闭）；不按距离、不显示在线状态 |
| **想再约** | 评价时可选“下次还想和 TA 打”；只有双方都选了才告诉双方，一方选了谁也不知道 |
| 隐私设置 | “在同馆常客里显示我”（默认关）、“允许同球群的人发消息请求”（默认开） |

### 12.3 以后再做 / 不做

- **下一步**：球馆页的本周公开局汇总、“谢谢这场球”（只有本人看得到数量）、群内出勤榜（可关闭）、好友动态（只放打完球自动生成的卡片，本人开启）。
- **以后**：群内帖子和照片、群内阶梯赛、关注俱乐部/教练（等球群足够活跃）。
- **不做**：全站动态广场、水平排行榜、“附近的人”、在线状态、陌生人随意私信、单向关注个人。

实现：`Models/PlayGroup.swift`、`Services/Backend/MockBackend+Groups.swift`、`MockBackend+Conversations.swift`（`MessagePermission`）、`Features/Groups/`、`Features/Messages/GroupChatView.swift`、`Features/Social/ProfileLink.swift`。

## 13. 等级：1–9 级 × 三档（27 档），高水平只认证据

> 问题来源：①“应该用清晰的等级制度划分实力，让人可以对照着写，然后自动生成 1–9 级。”②“达到高等级之后，等级之间差距有点大……可以分得更细：1−、1、1+；最高级是世界一流水平，必须是 BWF 上能找到的注册球员。”
> 第一版的问题：7–9 级只有三格，“A 组前四”和“有 BWF 排名”挤在相邻两级；9 级只到“Open 组获奖牌”，不是世界水平。

### 13.1 依据

| 结论 | 证据 |
|---|---|
| 没有通用的业余等级标准 | 中国羽协业余等级（2019 试行）是“九级最低”，最高到四级，全部低于三级运动员 [官方]；民间常用中羽在线 0–9 级、打球吧“业余 1–9 级”（每级有可数的测试）[社区]；美国赛事只有 Open 组由 USAB 认证，B–E 组由赛事总监分组，各地的 A 组强度不同 [USAB 规程、用户] |
| 让人直接挑等级不准 | 自评与实际表现相关仅 r≈0.29 [Mabe & West 1982]；水平越低越容易高估 [Heck 等 2025]；题目越具体、越可核验，自评越准 [Zell & Krizan 2014] |
| 同伴评价比自评可靠 | 与上级评分的一致性：同伴 ρ=0.62，自评 0.35 [Harris & Schaubroeck 1988] |
| 分项描述有社区共识 | 中羽在线论坛流传的 1–9 级分项描述（步法、发力、正反手后场、网前、中场、攻防、战术、双打），社区广泛引用 [社区]；它的 6 级是“俱乐部霸主 / 准霸主”、7 级是业余上限且需要一两项绝活，和我们的 6、7 级定义一致 |
| 子档是成熟做法 | NTRP 每级内部再分百分点、对外只公布 0.5 级 [USTA]；UTR、DUPR、Playtomic 用小数 [官方/平台]；法国羽协每级分 3 个子档、按排名百分位划分 [FFBaD]；中羽在线 4+ = “全部达 4 级且 1–2 项达 5 级” [社区] |
| 只有 BWF ID 不够 | 美国选手经 USAB 申请 BWF ID；报世界老将锦标赛同样要 BWF ID [USAB]。所以 9 级只认世界排名名次或成年组正赛战绩 |
| 世界排名的分布 | 52 周内打过任一计分赛即上榜，只计最好 10 站 [BWF 规程]。男单约 1,860 人上榜，第 20 / 100 / 500 名约 5.4 万 / 1.7 万 / 1,800 分；美国五项进前 100 的只有 8 个条目 [第三方按 BWF 规则重算，需人工复核] |
| 中国运动员技术等级（2025 版） | 国际级运动健将：奥运会/世锦赛前 8、Super 750 及以上前 4 等；运动健将：全国锦标赛前 16 等；一级 / 二级 / 三级按全国、省级赛名次 [体竞字〔2024〕121 号]。2025 起为 15 位电子证书，末位是等级码；旧证书门槛低很多 [官方] |

### 13.2 27 档

- **刻度**：内部是连续分值（4− = 3.67，4 = 4.00，4+ = 4.33），显示时取最近的一档（`SkillTier`）。
- **3–6 级一级比一级多一个维度**（产品定义，2026-10-14 按用户反馈修订）：技术“会不会”在 4 级就全部解决（包括反手）；4、5 级在技术上比的是**主动球 vs 被动球、极限球**——4 级主动球都会但被动球做不到，5 级被动球有机会摆脱，技术特点和战术开始明显。

| 档 | 名称 | 标准 |
|---|---|---|
| 1− … 2+ | 萌新 / 入门 | 发球进区、高远到后场、慢速对拉的个数 |
| 3− | 初级 | 技术学了大半，还有一两项不会（常见是反手、发力） |
| 3 | 初级 | 全部技术都会做（所有分项到 3 级），但质量一般 |
| 3+ | 初级 | 全部技术都会，一两项打得不错（到 4 级），但稳定性不足 |
| 4− | 中级 | 多数分项到 4 级，个别还在 3 级 |
| 4 | 中级 | 主动球全部不错（所有分项到 4 级，包括反手），双打有基本意识；但被动球、极限球做不到 |
| 4+ | 中级 | 主动球全部不错，一两项精通（到 5 级），稳定性略有提升；被动球仍是短板 |
| 5− | 中高级 | 被动球、极限球有时能过渡出来（回到对方后场或网前，让自己回位） |
| 5 | 中高级 | 被动球多数能摆脱；技术特点和战术开始明显 |
| 5+ | 中高级 | 战术和技巧明显结合：落点、节奏、假动作，随对手调整 |
| 6− | 崭露头角 | 和俱乐部里最强的几个人互有胜负；多数分项到 5 级，多拍很稳 |
| 6 | 俱乐部高手 | 俱乐部准霸主，日常局很少输；有一两项到 6 级的绝活 |
| 6+ | 俱乐部顶尖 | 俱乐部霸主，俱乐部对抗的主力，开始打业余 / 半专业比赛 |
| 7− | 准州级 | 州 / 地区赛次高组冠军或最高组正赛赢球；三级运动员（2025 新标准）、旧二级 |
| 7 | 州级选手 | 州 / 地区公开赛最高组 8 强；二级运动员（2025 新标准） |
| 7+ | 州级精英 | 州 / 地区公开赛最高组 4 强或冠军 |
| 8− | 准国家级 | USAB 认证赛最高组正赛赢 1 场（进入 USAB 排名表）；2025 年前的一级证书 |
| 8 | 国家级 | USAB 全国排名正式名次，或认证赛最高组 8 强；一级运动员 |
| 8+ | 国家顶尖 | USAB 任一项目前 5，或全国成年锦标赛 4 强；运动健将 |
| 9− | 国际选手 | BWF 世界排名前 500，或单站 ≥1,370 分（International Series 8 强、IC / Super 100 正赛赢 1 场） |
| 9 | 国际职业 | BWF 世界排名前 100，或 Super 300 及以上正赛赢 1 场 |
| 9+ | 世界顶尖 | BWF 世界排名前 20，或奥运会 / 世锦赛 8 强、Super 750 及以上 4 强（国际级运动健将成绩线） |

  组别按“最高组 / 次高组”的相对位置认定（各地 A 组强度不同）；签表要 ≥8 人，7 起 ≥16 人。BWF 证据看近 24 个月。二级运动员从调研建议的 8− 调到 7（州级），8、9 级其余不变。

### 13.3 怎么得到等级

- **问卷（14 题，一次一题，可以暂时跳过）：每个选项对应一个等级**（2026-10 按用户标定重做；旧版中间选项就算 4 级，随手一填就到 5，太松）：
  1. **一题只问一个技术或能力**，选项是能不能做到某个具体动作，不让用户自己总结“某方面怎么样”。技术 7 题：正手高远球、正手杀球、正手吊球（会不会劈吊、滑板）、反手后场、网前搓放、平抽挡、步法；比赛能力 4 题：接杀和被动球、双打、稳定性、战术（选项参考中羽在线论坛流传的分项描述 [社区]）。
  2. **每个选项标一个等级，可以是半级**（“底线到底线” = 3、“能杀下去、有一定球速但对方不难接” = 2.5、“劈吊滑板都熟练、和高远杀球动作一致” = 6）。高远、杀球、吊球、反手四题的分值是用户逐项标的；其余各题按同样的尺度定，等用户确认。
  3. **技术、比赛能力各算一个水平**：取平均，但不能比自己最弱的一项高出 1 级以上（反手只能绕头的人，别的再好也到不了 3）。**两者以弱的为准**，强的那边最多再加 2/3 级（技术 4 级、比赛能力只有 3 级 → 4−）。结果按 1/3 级取整，所以 −、+ 是算出来的，不是拍脑袋。
  4. **5+ 往上看俱乐部里的位置**：位置只到“中上游”最多 5+；崭露头角 → 最多 6−，准霸主 → 最多 6，霸主 → 6+（还要有比赛或青训经历）。位置最多把结果往上推一档，技术和比赛能力没到的，位置再高也不算 6 级。
  5. 比赛、训练经历给保底；保底比结果高 2 级以上标记“待校准”；回归球友保底减 1 级。
  6. 结果页写出下一档要补的最弱几项（“想到 4 级先补短板：接杀和被动球、双打”）。
- **男女分开算**（2026-10 用户决定）：羽毛球男女差距很大，等级按性别各自算（女子 4 级是女生里的强手，问卷题目一样）。
  - 注册时必选男 / 女，注明“只用来定级和公平匹配，不代表性别认同”，设置里可以改；以前注册的人打开 App 先补选。
  - 男女同场时换算到同一把尺子：**女子等级 − 1.5 ≈ 男子等级**（用户的经验：男子三级单打能赢女子四级）。快速匹配、“水平相近”的约战、战绩里的对手强弱都按换算后比；以后用真实赛果校准这个差值。
  - **项目**（2026-10 用户要求）：约球和开局选“项目”：单打是不限 / 男单（或女单），双打是不限 / 男双（或女双）/ 混双，只显示自己能参加的。双方的要求都要满足（双打四个人两两满足）。
  - **混双**：四个人两男两女，每边一男一女；男生和男生比、女生和女生比，所以等级不换算，各按各的。分边时强的男生配弱一点的女生。混双的约球只和混双的配；混双局男女各两个位子，满了的那边公开局进候补（空出来只补同一边），私密局直接提示满了。
  - 公开局、球群可以设成只限女生（或男生，只能选自己的性别）：别人看不到、进不去；只限女生的局按女子等级定范围，男女都能来的局按男子等级（女生换算后比）。球群没有混双（每周来的人不固定）。
  - 排行榜男女分开排，默认看自己的榜，可以切换；资料页显示是男子还是女子等级；举报原因多了“性别不实”，防止冒充进女生局。
- **暂时跳过**：注册时可以跳过定级，先按 Lv.3 匹配，球友评价占 85% 加快校准；“我的”页和编辑资料页提示“去定级”，补测不受 90 天限制。
- 结果页显示 7 个技术各在哪一档（“反手后场 3−”），最强的标为“技术特点”，最弱的标为短板。
- 对照表每一级都可以展开“分项标准”（1–6 级各分项的样子；7–9 级的技术、战术、稳定性和背景描述，7 级附中羽的自测参考：和全国性业余赛冠军对打，21 分制输分不超过 10 分）。
- **问卷最高 6+**，球友评价最多推到 7−；顶到 6+ 的人球友评价权重提到 85%。
- **球友评价**：打满 5 场后，等级 = 问卷 30% + 球友评价 70%（待校准、回归球友、顶到 6+ 的为 15% + 85%）。赛后评价的“比标的低 / 高”各移动一档，也可以精确到档。
- **认证**（`VerificationView`，人工审核）：tournamentsoftware 公开成绩（7−–8）、USAB 全国排名或运动员等级电子证书（7−–8+，证书编号末位决定上限：三级 7−、二级 7、一级 8、运动健将 8+）、bwfbadminton.com 球员页（9−–9+）。审核核对证据上的姓名与证件。
- **显示规则**：没认证最高 7−；认证后以认证档位为上限，球友评价最多往下调 1 档。
- **匹配按档位**：“水平差 1 级”= 上下 3 档（4+ 匹配 3+ 到 5+）；双打分组按连续分值平衡。

实现：`Models/SkillTier.swift`、`Models/User.swift`（`SkillLevel`、`VerificationStatus`、`displayTier`）、`Models/SkillAssessment.swift`、`Models/Verification.swift`、`Services/Backend/MockBackend+Verification.swift`、`Features/Onboarding/SkillAssessmentViews.swift`、`Features/Profile/VerificationView.swift`。

> 推断与未核实：3–6 级的定义是产品决定，分项描述来自中羽在线论坛（社区共识，不是官方标准），问卷的分值和门槛要用真实球友评价校准；中羽把二级运动员放在 7+、三级放在 6 级的目标，我们按用户定义放在 7 和 7−；美国组别对应、7 级的门槛、旧证书降一档、证据有效期 24 个月都是推断，上线后要用真实赛果校准。BWF 2026 版排名规程、2021 版羽毛球等级标准原文、运动员技术等级系统的公网地址未能读取。以后改用赛果算分时，可按 1 级 ≈ 200 Elo、1 档 ≈ 67 分换算，并像 TrueSkill / Glicko 一样显示保守值、在档界留缓冲，避免等级来回跳。

## 14. 胜率、排行榜与约战

参考对象和取舍（调研看的是真实用户反馈，不是官方宣传）：

- **赛果靠双方确认**（DUPR、Playtomic、Rank ID 都这么做）：结束球局的人先报“我方赢 / 输 / 友谊局”，其他人看到预选好的结果，点“对”或改成自己记得的。两队各至少一人报、且一致才计入；打了好几局按赢得多的一方算。**记不清**的人选“记不清了”：不算确认也不算分歧，这场不计入。说法不一致是“有分歧”，7 天内任何人都能改，改到一致照常计入；7 天内没确认就作废，**不做超时自动确认**，虚报不会因为对方没理会而生效。“先报后确认”的检验来自激励：要计入，输的一方得亲口认输。DUPR 用户最不信任的就是“专挑弱手刷分”和小号，所以下面每条规则都针对这两点。
- **月度胜率**（资料页，每个自然月重算）：满 5 场才公开，且一定带上样本——场数、不同对手数、对手平均比你强/弱多少。同一对手每月最多计 3 场。只看胜率最好懂但最容易刷，把对手强度摆出来，刷的人一眼就能看出来；暂不公开 Elo 分值（DUPR 因“赢了还掉分”被大量投诉）。
- **场馆月榜**：学 Strava Local Legends，比的是“本月在这家馆打了多少场确认过的球”，不比谁赢得多，休闲球员也有机会；按水平段（1–2 / 3–4 / 5–6 / 7+）分开排，每段第一是“本月馆主”。同一对手最多计 4 场、每天最多 3 场；至少 3 场、2 位不同对手才上榜。
- **全球周榜**（UTC 周一重置）：每场确认过的比赛输 10 分、赢 15 分，乘对手强度系数（0.5–1.5，打强手多得、打弱手少得），同一对手第 2 场减半、第 3 场起不计，每周最多计 15 场；至少 3 场、2 位对手才上榜。输球也得分，鼓励多打；场次封顶避免“肝”（Duolingo 联赛的教训）。可切换全球 / 本国 / 只看我的水平段，总能看到“我的位置”（研究显示排在后面的人看不到自己会失去动力）。
- **防刷、防广告**：注册满 7 天才上榜；昵称和简介不能留联系方式或链接（榜单只显示昵称、等级、头像）；榜单上可举报，举报后先对举报人隐藏、进入人工复核；用户可以在设置里关闭上榜。**故意拒认**：近 60 天和至少 3 位不同对手有到期仍未解决的赛果分歧的人暂不上榜（期限内还能改的不算，记不清也不算）（本人看得到原因），人工核实后恢复——单次争议谁对谁错无法判断，但总和不同的人起争议本身就是信号。真实服务端还要做：封闭小圈子检测（一群人只互相打）、同设备多账号、作弊处理后给受影响的对手退分。
- **点头像约战**：对方资料页上有“发起单打挑战”。谁能挑战我由我决定：所有人 / 水平相近（默认，±1 级）/ 仅球友 / 不接受；不接受时别人根本看不到按钮。对方 48 小时内回应，拒绝和超时对发起人都显示“未成行”；同时最多发出 3 个、对方最多积压 3 个待处理、每天最多 5 个，被拒后 7 天内不能再挑战同一人；只能挑战同一国家/地区的人。接受后生成一场球局，照常双方确认赛果。也可以发起双打挑战：发起人带一位球友做搭档，对方接受时选自己的搭档（都必须是各自的球友）。

## 15. 走向全球

- 模拟世界、球馆、榜单都跟着用户所在位置走；约战、榜单“本国”都以国家/地区为界，不跨国匹配。
- 已支持的国家/地区（手机号、货币、地址顺序、导航 App）：美、加、中、港、台、新、马、日、韩、英、澳、印、印尼、泰、越、菲、丹、新西兰、德、法；其他国家走通用规则。
- 美国业余赛组别（“大致相当于 D 组”）只对美国地区显示。
- 美国以外的球馆靠 Apple 地图搜索 + 球友添加；人工核实的精选球馆目前只有美国。吉隆坡 / 巴生谷预置了 28 家来自 OpenStreetMap 的羽毛球馆（去掉商店、泛称、学校与协会场地，地址由 Nominatim 反查），状态是“待确认”，详情页注明 © OpenStreetMap 贡献者（ODbL）。- **各地球馆数据按“当地人从哪里找场地”来选来源**，优先政府开放数据（可商用、有署名要求），商业订场平台（Courtsite、AYO、Playo、Hudle、趣运动、大众点评等）条款禁止抓取，只谈合作：
  - 香港：康文署 SmartPLAY 羽毛球场开放数据（105 个可订场馆，含场数；DATA.GOV.HK）
  - 新加坡：Sport Singapore「Sport Facilities」+「SportSG Sport Facilities」（ActiveSG 体育中心 + 设羽毛球场的社区中心共 119 个；私人公寓的场地不对外，已排除；Singapore Open Data Licence）
  - 台湾：运动部「全國運動場館資訊」中对外开放、有羽球设施的 633 个场馆（政府資料開放授權條款）
  - 英格兰：Sport England Active Places 中营业中、个人可直接订（Pay and Play / 会员制）且有羽毛球场的 1,553 个场馆（CC BY 4.0；联系人等个人字段不导入；只租给俱乐部的学校场馆不收录）
  - 美国：没有全国性的开放数据。Overture Maps Places（CDLA-Permissive-2.0）里名称或分类含羽毛球的地点只当线索（实测约一半是商店、重复、停业或位置不准），逐家对照球馆官网、预订页、市政府和学校页面核实，来源和核实日期记在 `data/us_venues.json`，坐标用美国人口普查局的地址编码。除专营球馆外，也收录社区中心、学校等只在固定时段开放羽毛球的地方，标出类型和时段。第三方名录（badmintonclubs.org、badmintonjustin.com、worldbadminton.com）条款禁止抓取或未授权，不作为来源，已去信申请授权。2026-10 按州核实了 34 个州 276 处（加州 74、德州 29、伊利诺伊 24、华盛顿 23、马里兰 21、新泽西 17、纽约 16 …），其中专营馆 105、社区中心 123、学校 21、综合馆 25、社区会馆 2。不少市政府网站拒绝自动访问（403），这些城市的 drop-in 要人工查看；San Antonio、Tulsa、Cleveland、Cincinnati、Milwaukee、Miami、Tampa 等暂时没有找到可核实的公开场地。
  - 这些数据由 `scripts/build_open_data_venues.py` 生成 `Badie/Resources/venues-XX.json`，随 App 只读发布，不写进本地数据库；球友确认、签到时才复制进库。详情页显示各数据集要求的署名。
  - 东京：各区市「公共施設一覧」（CC BY 4.0）里的 58 个公共体育馆（不含学校）。数据不标运动项目，详情页注明以馆方为准。
  - 韩国：문화체육관광부「전국 공공체육시설 현황」(2021) 里写明能打배드민턴 的 975 个场馆。原表没有坐标，先放在所在区的中心、不显示；用户到附近时 App 用 Apple 地图按名称找到对应地点，核对上了才显示（采用 Apple 的坐标和地址），找不到的 30 天后再试。
  - 其他地方：用户到一个新地区、出行范围内收录少于 8 家时，App 用当地叫法搜 Apple 地图（最多 3 个词），名称里明确是羽毛球场地的（badminton / 羽毛球 / 배드민턴 / bulu tangkis / GOR / cầu lông …）直接收录为“待确认”，综合体育馆之类不猜；Google 地图需要付费 API key，且条款禁止批量存储，不用。
  - 中羽在线的场馆库（badmintoncn.com/cbo_gym）有反爬验证，属于网站方的用户贡献数据，未经授权不能抓取（国内有爬取点评数据被判不正当竞争的判例）；可以谈合作。
  - 还没做的：日本东京以外、韩国更新的数据（data.go.kr 全国体育设施 API，需要申请 key）、加拿大（StatCan ODRSF）、澳洲维多利亚州；马来西亚、印尼、泰国、越南、菲律宾、印度没有可用的官方数据，只能 OSM + 球友添加；中国大陆没有可商用的开放数据，暂靠球友添加；丹麦 Idan 设施库需要签协议。Apple 地图没有“羽毛球”分类，只能按名称匹配，所以附近建议会同时用英文和当地叫法搜（bulu tangkis / GOR、sân cầu lông、バドミントン、배드민턴、แบดมินตัน、羽毛球馆…，最多 3 个词，受 Apple 频率限制）。覆盖率仍取决于 Apple 地图本身；下一步按城市从 OpenStreetMap（sport=badminton，ODbL 需署名）预置球馆，正式上线后再考虑 Google Places（按次收费、限制存储）。
- 上线顺序建议：英语可用、WhatsApp 习惯的新加坡 / 马来西亚，再到英国（以俱乐部工具切入）。中国大陆需要本地主体、ICP 备案和小程序，单独立项；欧盟要 GDPR 合规包，印度 DPDP 核心义务约 2027 年生效。

## 16. 已知限制

- **没有真实服务端**：附近球友、公开球局为本机模拟（设置页明确告知），可“重置演示数据”。`MockBackend` 以事件流对外，替换为真实 API 时 Manager 层无需改动。正式后端的选型、球馆共享方式、改造步骤与中国合规清单见 [BACKEND.md](BACKEND.md)。
- **支付**：AA 只做“已付/待付”标记，未接入真实支付。
- **球馆库目前只在本机**：添加、确认、举报都写入本机模拟后端；多人共享需要真实服务端与人工审核队列。
- **Apple 地图数据条款**：Place ID 可长期保存；其余地图内容（名称、地址、坐标）条款上只允许临时缓存，正式上线前需法务确认“用户确认后入库”的做法。
- **Place ID 需要 iOS 18**：iOS 17 设备只能靠坐标 + 名称查重。
- **匹配通知目前只在 App 内**：找到搭子、补位、约成都会写入通知中心并弹提示；系统推送需要真实服务端（APNs）。模拟球友会在几秒到十几秒内回复，并会陆续“发布空闲时间”。
- **球群的场次没有生成“球局”**：报名、候补、递补、临时取消已经可用，但签到、AA 和赛后互评目前只在快速匹配和房间生成的球局里有；下一步让每一场固定局也能签到、互评。
- **群号邀请链接**：现在分享的是带群号的文字（微信里最常用），还没有可点击的深链接（需要配置 Universal Links 域名）。
- **“此刻也在找人”在演示模式里是模拟的**：球友池按时间段随机生成；正式后端里就是此刻挂着请求的真实用户（普通请求开赛前 2 小时已结束，临时局之间互相匹配）。
- 认证申请目前只在本机记录（演示用的审核函数 `reviewVerification`）；正式上线需要运营后台、证件核对流程，以及 BWF / USAB 排名的人工复核。
