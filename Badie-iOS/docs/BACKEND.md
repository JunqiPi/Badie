# Badie 正式后端规划

> 状态：规划稿（2026-10）。现在的 App 用本机模拟后端 `MockBackend`，所有数据只在自己手机上；
> 本文规划换成真正的共享后端。线路延迟、价格多来自厂商资料，合规部分不是法律意见，决策前需晚高峰实测并咨询律师。

## 1. 为什么现在要做

只有共享后端才能让“一个人添加的球馆，下一个人也能看到并发起匹配”。匹配、聊天、排行榜防作弊也都依赖服务端。

## 2. 选型结论

| 方案 | 结论 | 主要原因 |
|---|---|---|
| **自建 Supabase（开源版），阿里云/腾讯云香港，自有域名** | **推荐** | Postgres + PostGIS + Auth（Apple 登录）+ Realtime + Storage 一套齐；香港不需要 ICP 备案，回大陆线路较好；自有域名避开共享域名被整体封锁的风险 |
| 托管 Supabase（东京）+ 自定义域名 | 备选（不想运维时） | 国内开发者普遍反馈直连海外节点慢且不稳（有实测迁自建后 REST 从约 700ms 降到 50–100ms）；`*.supabase.co` 2026 年 2 月在印度被整域封过 |
| Firebase | 排除 | 大陆基本连不上 |
| CloudKit | 排除 | 公共库没有服务端逻辑（排行榜无法防作弊），地理查询精度粗，无法扩展到 Android/Web |
| 大陆节点 | 暂缓 | 需要境内主体做 ICP 备案 |

## 3. 第一期架构

```
iOS App ──HTTPS/WebSocket──> api.<自有域名>（香港，精品/CN2 线路）
                               ├─ Postgres + PostGIS（数据、ST_DWithin 查附近球馆）
                               ├─ GoTrue Auth（Apple 登录、邮箱验证码）
                               ├─ Realtime（聊天、匹配状态）
                               ├─ Storage + CDN（头像）
                               └─ 业务服务（TS 或 Go）：赛果确认、榜单、匹配、限流、APNs 推送
```

- **客户端只提交，服务端计算**：赛果确认、胜率、场馆榜、周榜、挑战限额、匹配都在服务端算。客户端里的 `Rankings` 等规则代码保留，用于界面预览，并作为服务端实现的参考。
- **权限**：所有表开行级权限（RLS）；写操作走服务端函数，不让客户端直接改别人的数据。
- **推送**：服务端直连 APNs；iOS 不需要国内推送 SDK。上线前在大陆三网真机实测。
- **欧美用户**：多 150–200ms，对约球、聊天可以接受；以后量大再加区域。

## 4. 球馆共享（第一期最先上线的部分）

| 来源 | 存什么 | 共享方式 |
|---|---|---|
| 开放数据（HK/SG/TW/GB/东京/韩国） | 仍随 App 打包 | 不进服务器，按许可显示署名 |
| 用户手动添加 | 用户填的名字、地址、图钉坐标 | 存服务器，附近所有人立即可见（“待确认”），3 位不同球友在这里打过/确认后变“球友确认” |
| 用户从 Apple 地图选点添加 | **只存 Apple Place ID** + 用户确认的名字和位置 | Apple 允许长期保存 Place ID；其他人的手机用 ID 向 Apple 取最新详情 |
| App 自动从 Apple 地图收录 | 只在本机缓存 | **不上传服务器**（Apple 条款不允许批量存储、再分发它的数据）；有人在这家馆发起匹配时，才作为“用户选点添加”上传（只带 Place ID） |

去重：服务器端按 Place ID、名称相似度、距离（< 80m）判重，复用现在 `VenueSearch.duplicates` 的规则。

## 5. 数据表（对应现在的 `Database`）

第一批：`users`、`venues`（`geography(Point)` 列 + GiST 索引）、`venue_reports`、`favorites`、`friendships`、`friend_requests`、`blocks`、`reports`。
第二批：`tickets`、`offers`、`games`、`result_reports`、`match_records`、`challenges`、`surveys`。
第三批：`threads`、`messages`、`groups`、`group_sessions`、`inbox`、`verification_requests`。

`bots`、`seededUserIds` 等演示数据只留在 `MockBackend`。

## 6. App 端改造步骤

1. **抽协议**：现在 `AppState`、各个 Manager 直接依赖 `MockBackend` 这个具体类（约 190 个方法）。先按领域拆出 `VenueService`、`GameService`、`SocialService` 等协议，`MockBackend` 实现它们，行为不变，测试照常跑。
2. **实现 `RemoteBackend`**：用 supabase-swift 或手写 URLSession，逐个领域接上；用开关切换模拟/正式，演示模式和 CI 截图继续用模拟后端。
3. **按“球馆 → 账号与资料 → 匹配与对局 → 赛果与榜单 → 聊天与球群”的顺序上线**，每一步都能单独发布。

## 7. 成本（粗估，每月）

| 规模 | 自建香港 | 托管 Supabase |
|---|---|---|
| ~1k 月活 | 2C4G 一台 + 对象存储备份，约 US$10–30 | Pro US$25 |
| ~5 万月活 | 4C8G 精品线路 + 数据盘 + CDN，约 US$80–200（香港精品带宽是主要变量） | 约 US$80–150 |

## 8. 中国合规清单

1. **先定运营主体**。境外主体目前多能在国区上架，但被要求补 ICP 备案号、被下架的风险一直在（2023 年 9 月起苹果要求国区 App 提供备案号，2025 年已有个人开发者因此被下架）。要长期稳定服务大陆，需要境内合作主体做 App 备案，后端也可能要迁到大陆。
2. **两份隐私政策**：英文版 + 符合《个人信息保护法》的中文版，写明数据存放在香港及出境用途，并取得单独同意。
3. **不收集敏感个人信息**：精确位置轨迹属于敏感信息。服务器只存场馆坐标和粗略城市，不存用户实时位置；“附近”的计算尽量在手机上做。这样在 10 万人以内可以适用数据出境的豁免。
4. **审核能力**：举报处理、删除内容、封号，并留存日志。
5. **实名**：大陆备案后需要手机号认证；第一期先预留字段。大陆短信需要境内主体签名，暂缓。
6. **苹果要求**：App 内删除账号、提供 Apple 登录。
7. **上线前实测**：大陆电信、联通、移动三网晚高峰，测 API、WebSocket、APNs、头像加载。
