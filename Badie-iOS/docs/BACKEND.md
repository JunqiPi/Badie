# Badie 正式后端规划

> 状态：规划稿（2026-10）。前提：个人开发、纯非营利、预算尽量低。
> 现在的 App 用本机模拟后端 `MockBackend`，所有数据只在自己手机上；本文规划换成真正的共享后端。
> 价格与线路数据多来自厂商和社区帖子，下单前需晚高峰实测；合规部分不是法律意见。

## 1. 会有多少人用（按这个规模设计，不为百万用户过度设计）

| 情景 | 月活 半年 / 1 年 / 2 年 | 2 年时高峰同时在线 | 高峰请求/秒 |
|---|---|---|---|
| 悲观（没打进任何球群） | 100 / 300 / 500 | ~10 | <2 |
| **可能**（1–3 个城市、几家俱乐部用起来） | 800 / 2,000 / 5,000 | ~100 | ~15 |
| 乐观（打通球馆/俱乐部，口碑扩散） | 5,000 / 15,000 / 50,000 | ~1,200 | ~200 |

依据：不投营销的独立 App 首年下载中位数大约在 1,000 以内；同类产品里 Spond 用约 10 年做到 330 万月活，Reclub 用 7 年做到 80 万+ 安装，都是靠俱乐部组织者整群迁入。
估算假设（无公开数据可核）：约球是低频需求，日活/月活取 15–25%；每个日活每天 50–100 次请求；晚 7–10 点高峰占全天 20%，突发按 3 倍。

**结论：真正的瓶颈是冷启动（每个城市先要有足够多的人），不是服务器。** 一台小服务器能撑到乐观情景的第 1 年。

## 2. 选型结论

| 方案 | 结论 | 原因 |
|---|---|---|
| **Go 单程序（PocketBase 作为框架）+ SQLite，腾讯云轻量香港** | **推荐** | 内存几十 MB，一台 2C2G 就够；自带 Apple 登录、实时推送、文件存储、管理后台（审核举报直接用）；香港不需要 ICP 备案、回大陆延迟较低 |
| 自建 Supabase | 放弃 | 官方要求至少 4GB 内存、十几个容器，个人运维太重 |
| 托管 Supabase | 放弃 | 免费版 7 天无请求就暂停（App 直接不可用）；Pro 版每月 25 美元；大陆访问慢 |
| Firebase | 放弃 | 大陆基本连不上 |
| Cloudflare Workers / D1 | 放弃 | 免费用户没有中国节点，大陆延迟 200–300ms |
| Oracle 永久免费机 | 只做冷备/测试 | 闲置会被回收、有无故封号报告、常开不出实例 |
| 阿里云轻量香港 | 备选 | 价格接近，但多人反映被限速到 3–10M、电信晚高峰丢包 |
| CloudKit | 放弃 | 没有服务端逻辑，排行榜无法防作弊 |

## 3. 架构

```
iOS App ──HTTPS / SSE──> api.<自有域名>  （腾讯云轻量香港 2C2G）
                           Nginx（TLS、头像缓存；SSE 需关掉 proxy_buffering）
                           └─ badie-server（Go，一个可执行文件）
                                ├─ PocketBase：Apple 登录、数据表、权限规则、实时订阅、文件、管理后台
                                ├─ 业务代码：赛果确认、胜率/榜单（定时计算写表）、匹配、限流、挑战规则
                                ├─ 附近查询：SQLite R*Tree / 经纬度范围索引 + 球面距离二次过滤
                                └─ APNs 直连推送
                           SQLite ──Litestream 实时备份──> Cloudflare R2（10GB 内免费）
```

- **客户端只提交，服务端计算**：赛果、胜率、榜单、挑战限额、匹配都在服务器算。App 里的 `Rankings` 等规则代码保留做界面预览，也是服务端实现的参考。
- **头像**：App 端压缩到 30KB 以下，存在同一台服务器，由 Nginx 缓存输出（R2 从大陆访问晚高峰慢，只做备份）。
- **聊天**：先用 PocketBase 自带的实时订阅（SSE）；App 在后台时由 APNs 推送。
- **审核**：直接用 PocketBase 管理后台处理举报、删内容、封号，不用另写运营后台。
- **欧美用户**：多 150–200ms，约球、聊天可以接受。

## 4. 球馆共享

| 来源 | 存什么 | 共享方式 |
|---|---|---|
| 开放数据（HK/SG/TW/GB/东京/韩国） | 随 App 打包 | 不进服务器，按许可显示署名 |
| 用户手动添加 | 用户填的名字、地址、图钉坐标 | 存服务器，附近的人立即可见（“待确认”），3 位不同球友确认后变“球友确认” |
| 用户从 Apple 地图选点添加 | **只存 Apple Place ID** + 用户确认的名字和位置 | Apple 允许长期保存 Place ID；别人的手机用 ID 向 Apple 取最新详情 |
| App 自动从 Apple 地图收录 | 只在本机缓存 | 不上传（Apple 条款不允许批量存储再分发）；有人在这家馆发起匹配时，才作为“选点添加”上传 Place ID |

去重：服务器端按 Place ID、名称相似度、距离（< 80m）判重，规则同 `VenueSearch.duplicates`。

## 5. 数据表（对应现在的 `Database`）

第一批：`users`、`venues`、`venue_reports`、`favorites`、`friendships`、`friend_requests`、`blocks`、`reports`。
第二批：`tickets`、`offers`、`games`、`result_reports`、`match_records`、`challenges`、`surveys`。
第三批：`threads`、`messages`、`groups`、`group_sessions`、`inbox`、`verification_requests`。
演示用的 `bots`、`seededUserIds` 只留在 `MockBackend`。

## 6. App 端改造步骤

1. **抽接口**：`AppState` 和各个 Manager 现在直接依赖 `MockBackend`（约 190 个方法）。先按领域拆出 `VenueService`、`GameService`、`SocialService` 等协议，`MockBackend` 实现它们，行为不变、测试照跑。
2. **实现 `RemoteBackend`**：用 URLSession 调服务器接口；开关切换模拟/正式，演示模式和 CI 截图继续用模拟后端。
3. **分块上线**：球馆 → 账号与资料 → 匹配与对局 → 赛果与榜单 → 聊天与球群，每一步都能单独发布。

## 7. 每月成本

| 规模 | 配置 | 服务器 | 加上 Apple 年费、域名摊销 |
|---|---|---|---|
| ~500 月活 | 腾讯轻量香港 2C2G（512GB 流量） | ~US$6 | ~US$15 |
| ~5k 月活 | 同一台，或 2C4G（2TB 流量） | US$6–15 | ~US$16–25 |
| ~5 万月活 | 4C8G；SQLite 写入成瓶颈时换同机 Postgres；头像加 CDN | ~US$36–60 | ~US$50–70 |

- **Apple 开发者年费 99 美元是最大的固定成本**，减免只给经认证的非营利组织，个人不行。
- APNs 免费；域名约 10 美元/年；备份在 10GB 内免费。

升级路径：同机升配 → SQLite 换 Postgres（地理查询代码保持可替换）→ 晚高峰投诉多时前置一台 CN2 GIA 线路反代 → 将来有了机构主体再考虑大陆机房。

## 8. 中国大陆：最大的限制在上架，不在服务器

- **中国区 App Store 上架必须有 ICP 备案号**（Apple 会核验）。备案要通过大陆接入商办理，香港服务器办不了。
- **个人主体基本备不了带聊天等用户内容的 App**（社区普遍经验，未找到官方原文，以当地通信管理局答复为准）。
- **所以第一期不上中国区 App Store**。大陆用户需要用其他地区的 Apple ID 下载；服务器在香港，使用不受影响。
- 将来要正式服务大陆：需要机构主体（公司或社团）做 App 备案，可能还要迁到大陆机房、加手机号实名。

其余合规：

1. 隐私政策中英两版，中文版写明数据存放在香港及用途，并取得单独同意。
2. 不收集敏感个人信息：服务器只存场馆坐标和粗略城市，不存用户实时位置，“附近”尽量在手机上算。
3. 举报、删除、封号能力，保留处理日志。
4. App 内可以删除账号；提供 Apple 登录。
5. 上线前在大陆三网晚高峰实测：接口、实时订阅、APNs、头像加载。

## 9. 下单前要做的

- 先用按量计费开一台腾讯轻量香港，在晚上 8–11 点用 mtr 测电信、联通、移动各 10 分钟，再决定是否包月。
- 注册域名，在 Apple 开发者后台创建“Sign in with Apple”服务和 APNs 密钥。
