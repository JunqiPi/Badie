# Badie 正式后端规划

> 状态：规划稿（2026-10）。前提：个人开发、纯非营利、预算尽量低；**先做中国大陆以外的全世界（大陆也能用），iOS + 同功能同风格的网页端**。
> 现在的 App 用本机模拟后端 `MockBackend`，所有数据只在自己手机上；本文规划换成真正的共享后端。
> 价格与线路数据多来自厂商和社区帖子，下单前需晚高峰实测；合规部分不是法律意见。

## 1. 会有多少人用（按这个规模设计，不为百万用户过度设计）

| 情景 | 月活 半年 / 1 年 / 2 年 | 2 年时高峰同时在线 | 高峰请求/秒 |
|---|---|---|---|
| 悲观（没打进任何球群） | 100 / 300 / 500 | ~10 | <2 |
| **可能**（1–3 个城市、几家俱乐部用起来） | 800 / 2,000 / 5,000 | ~100 | ~15 |
| 乐观（打通球馆/俱乐部，口碑扩散） | 5,000 / 15,000 / 50,000 | ~1,200 | ~200 |

依据：不投营销的独立 App 首年下载中位数大约在 1,000 以内；同类产品里 Spond 用约 10 年做到 330 万月活，Reclub 用 7 年做到 80 万+ 安装，都是靠俱乐部组织者整群迁入。
估算假设（无公开数据可核）：约球是低频需求，日活/月活取 15–25%；每个日活每天 50–100 次请求；晚 7–10 点高峰占全天 20%，突发按 3 倍。

**结论：真正的瓶颈是冷启动（每个城市先要有足够多的人），不是服务器。** 一台小服务器能撑到乐观情景的第 1 年。

## 2. 选型结论

| 方案 | 结论 | 原因 |
|---|---|---|
| **Go 单程序（PocketBase 作为框架）+ SQLite，一台小 VPS** | **推荐** | 内存几十 MB，2C2G 就够；自带 Apple/Google 登录、实时推送、文件存储、管理后台（审核举报直接用）；iOS 和网页共用同一套接口 |
| 自建 Supabase | 放弃 | 官方要求至少 4GB 内存、十几个容器，个人运维太重 |
| 托管 Supabase | 放弃 | 免费版 7 天无请求就暂停（App 直接不可用）；Pro 版每月 25 美元 |
| Firebase | 放弃 | 大陆基本连不上（大陆虽不是重点，但不想直接断掉） |
| Oracle 永久免费机 | 只做冷备/测试 | 闲置会被回收、有无故封号报告、常开不出实例 |
| CloudKit | 放弃 | 没有服务端逻辑，排行榜无法防作弊；网页端和安卓用不了 |

### 服务器放哪里

一台服务器服务全球，只能取折中。按第一批种子用户所在地选：

| 第一批用户主要在 | 选 | 到各地大致延迟 |
|---|---|---|
| 美国 | 美西（洛杉矶/硅谷） | 美国 20–70ms、欧洲 ~150ms、东亚 ~120ms、大陆晚高峰较差 |
| 东亚/东南亚 + 美国混合 | 东京 | 东亚 30–60ms、美西 ~100ms、欧洲 ~230ms、大陆尚可 |
| 大陆占比明显 | 香港（腾讯轻量 CN2） | 大陆/东南亚最好，欧美多 150–200ms |

约球、聊天对 200ms 以内的延迟不敏感，选错了以后也能整机迁移（SQLite 就是一个文件）。网页静态文件放全球 CDN，和服务器位置无关。

## 3. 架构

```
iOS App ─┐
         ├─HTTPS / SSE──> api.<自有域名>（一台 2C2G VPS）
网页端 ──┘                 Nginx（TLS、头像缓存；SSE 需关掉 proxy_buffering）
  ↑                        └─ badie-server（Go，一个可执行文件）
  │                             ├─ PocketBase：登录（Apple / Google / 邮箱验证码）、数据表、权限规则、实时订阅、文件、管理后台
  │                             ├─ 业务规则：赛果确认、胜率/榜单（定时计算写表）、匹配、限流、挑战规则
  │                             ├─ 附近查询：SQLite R*Tree / 经纬度范围索引 + 球面距离二次过滤
  │                             └─ 推送：APNs（iOS）+ Web Push（网页）
  │                        SQLite ──Litestream 实时备份──> Cloudflare R2（10GB 内免费）
  └── 静态网页：Cloudflare Pages（免费，全球 CDN）
```

- **规则只写一份，放在服务器**：赛果、胜率、榜单、挑战限额、匹配都在服务器算，iOS 和网页只负责显示和提交。现在写在 App 里的 `Rankings`、`Challenge`、匹配等规则代码，就是移植到 Go 的蓝本。
- **头像**：客户端压缩到 30KB 以下，存在服务器，由 Nginx 缓存输出。
- **聊天**：先用 PocketBase 自带的实时订阅（SSE）；不在前台时由 APNs / Web Push 推送。
- **审核**：直接用 PocketBase 管理后台处理举报、删内容、封号。

## 3.5 网页端（同功能、同风格）

| 项 | 做法 | 原因 |
|---|---|---|
| 框架 | **SvelteKit**（静态导出的单页应用）+ TypeScript | 打包小、手机浏览器上快；一个人写起来代码量少 |
| 托管 | Cloudflare Pages | 免费、全球 CDN |
| 风格 | 把 `Badie/DesignSystem/Theme.swift` 里的颜色、字号、圆角、描边、贴纸阴影导出成 CSS 变量，组件按 iOS 版一一对应 | 同一套设计语言；深色模式同样支持 |
| 地图 | **Apple MapKit JS** | 和 iOS 用同一份地图数据，**Apple Place ID 两端通用**，球馆去重规则不变；开发者账号自带免费额度（每天 25 万次地图加载、2.5 万次搜索类调用） |
| 多语言 | 从 `Localizable.xcstrings` 自动导出 10 种语言的 JSON | 翻译只维护一份 |
| 登录 | Apple + Google + 邮箱验证码 | 网页端主要服务安卓和电脑用户，不能只有 Apple 登录 |
| 推送 | Web Push（安卓浏览器直接可用；iPhone 需要“添加到主屏幕”，iOS 16.4+） | 免费 |
| 可安装 | PWA（可添加到主屏幕、离线显示上次数据） | 安卓用户不用等原生 App |

网页端最大的意义：**安卓用户第一天就能用**，不必再开发安卓原生 App。

## 4. 球馆共享

| 来源 | 存什么 | 共享方式 |
|---|---|---|
| 开放数据（HK/SG/TW/GB/东京/韩国） | 随 App 打包 | 不进服务器，按许可显示署名 |
| 用户手动添加 | 用户填的名字、地址、图钉坐标 | 存服务器，附近的人立即可见（“待确认”），3 位不同球友确认后变“球友确认” |
| 用户从 Apple 地图选点添加 | **只存 Apple Place ID** + 用户确认的名字和位置 | Apple 允许长期保存 Place ID；别人的手机用 ID 向 Apple 取最新详情 |
| App 自动从 Apple 地图收录 | 只在本机缓存 | 不上传（Apple 条款不允许批量存储再分发）；有人在这家馆发起匹配时，才作为“选点添加”上传 Place ID |

去重：服务器端按 Place ID、名称相似度、距离（< 80m）判重，规则同 `VenueSearch.duplicates`。

## 5. 数据表（对应现在的 `Database`）

第一批：`users`、`venues`、`venue_reports`、`favorites`、`friendships`、`friend_requests`、`blocks`、`reports`。
第二批：`tickets`、`offers`、`games`、`result_reports`、`match_records`、`challenges`、`surveys`。
第三批：`threads`、`messages`、`groups`、`group_sessions`、`inbox`、`verification_requests`。
演示用的 `bots`、`seededUserIds` 只留在 `MockBackend`。

## 6. 开发顺序

1. **iOS 抽接口**（不需要服务器）：`AppState` 和各个 Manager 现在直接依赖 `MockBackend`（约 190 个方法）。按领域拆出 `VenueService`、`GameService`、`SocialService` 等协议，`MockBackend` 实现它们，行为不变、测试照跑。
2. **服务器第一块：账号 + 球馆**。Go + PocketBase，表结构、权限规则、附近查询、球馆去重和确认；先在本机和 CI 里跑测试。
3. **iOS 接上服务器**：`RemoteBackend` 按领域逐个接上；开关切换模拟/正式，演示模式和 CI 截图继续用模拟后端。
4. **网页端第一版**：登录、个人资料、附近球馆、添加球馆（和 iOS 同风格）。
5. **之后每块功能服务器先行、两端跟上**：匹配与对局 → 赛果与榜单 → 聊天与球群 → 挑战。每一步都能单独发布。

## 7. 每月成本

| 规模 | 配置 | 服务器 | 加上 Apple 年费、域名摊销 |
|---|---|---|---|
| ~500 月活 | 2C2G VPS（如腾讯轻量香港/硅谷/东京） | ~US$5–6 | ~US$15 |
| ~5k 月活 | 同一台，或 2C4G（2TB 流量） | US$6–15 | ~US$16–25 |
| ~5 万月活 | 4C8G；SQLite 写入成瓶颈时换同机 Postgres；头像加 CDN | ~US$36–60 | ~US$50–70 |

- **Apple 开发者年费 99 美元是最大的固定成本**，减免只给经认证的非营利组织，个人不行。
- APNs、Web Push、Cloudflare Pages、MapKit JS（免费额度内）都不花钱；域名约 10 美元/年；备份在 10GB 内免费。

升级路径：同机升配 → SQLite 换 Postgres（地理查询代码保持可替换）→ 某个地区用户多了再在那里加一台只读节点或反代 → 将来有了机构主体再考虑大陆机房。

## 8. 中国大陆：支持使用，但第一期不上中国区 App Store

- 中国区 App Store 上架必须有 ICP 备案号，备案要通过大陆接入商办理；个人主体基本备不了带聊天等用户内容的 App（社区普遍经验，以当地通信管理局答复为准）。
- 所以第一期 iOS 版不上中国区。大陆用户可以：用其他地区的 Apple ID 下载 iOS 版，或**直接用网页端**（服务器在境外，访问不需要备案）。
- App 内的大陆专用逻辑（中文搜索词、GCJ-02 坐标、Apple 地图数据源报错时的重试）继续保留。
- 将来要正式服务大陆：需要机构主体做备案，可能还要迁到大陆机房、加手机号实名。

其余合规：

1. 隐私政策：英文为主，覆盖 GDPR（英国/欧盟用户）、CCPA（加州）；中文版写明数据存放在境外及用途，并取得单独同意。
2. 不收集敏感个人信息：服务器只存场馆坐标和粗略城市，不存用户实时位置，“附近”尽量在手机上算。
3. 举报、删除、封号能力，保留处理日志。
4. App 内可以删除账号；提供 Apple 登录。
5. 上线前在主要市场实测：接口、实时订阅、推送、头像加载（大陆用户的体验也测一下）。

## 9. 下单前要做的

- 定下服务器地区后，先用按量计费开一台，在当地晚高峰测延迟和稳定性，再决定是否包月。
- 注册域名；在 Apple 开发者后台创建“Sign in with Apple”服务（含网页端回调）、APNs 密钥、MapKit JS 密钥；在 Google Cloud 创建 OAuth 客户端。
